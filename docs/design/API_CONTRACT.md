## 1. Base Configuration

### 1.1 Base URLs

| Environment | Base URL | Notes |
|---|---|---|
| Android emulator to local gateway | `http://10.0.2.2:3000` | `10.0.2.2` is the Android emulator alias for the host machine. |
| Physical Android device on LAN | `http://<HOST_IP>:3000` | Replace `<HOST_IP>` with the development workstation LAN IPv4 address. |
| Local gateway direct | `http://localhost:3000` | Use for curl, integration tests, and backend development. |
| Production | `https://api.<DOMAIN>/v1` | HTTPS is mandatory; TLS 1.2 or newer is required. |

The Android client resolves `API_BASE_URL` from a Gradle property, then an environment variable, then its emulator default. The gateway listens on port `3000` by default. [file:2]

### 1.2 Common request headers

| Header | Required | Value / rule |
|---|---|---|
| `Content-Type` | Required for requests with a body | `application/json` |
| `Accept` | Recommended | `application/json` |
| `Authorization` | Required for protected routes | `Bearer <jwt_token>` |
| `X-Request-Id` | Optional from client; always returned | Client UUID or server-generated UUID; maximum 128 characters. |
| `Idempotency-Key` | Required for `POST /candidate/swipes` | UUID v4 generated by the Android client for each user-initiated swipe action. |

The Android client sends JSON using Gson and adds `Authorization: Bearer <token>` when a token is available. Its swipe request sends a fresh UUID in `Idempotency-Key`; this is an idempotency key, not a distributed trace identifier. [file:2]

### 1.3 Common response headers

| Header | Rule |
|---|---|
| `Content-Type` | `application/json; charset=utf-8` |
| `X-Request-Id` | Echo a valid supplied request ID or generate a UUID; truncate supplied values to 128 characters. |
| `Cache-Control` | `no-store` for authenticated and personal-data responses. |

### 1.4 Authentication scheme

The Fastify gateway is the only client-facing trust boundary. It issues and validates JWT bearer tokens and owns all authorization decisions.

```http
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

| Property | Contract |
|---|---|
| Token format | JWT, signed with a server-controlled secret or asymmetric signing key. |
| Token carrier | `Authorization: Bearer <jwt_token>` header. |
| Token lifetime | Maximum 24 hours. |
| Token claims | `sub` (account ID), `role` (`CANDIDATE` or `RECRUITER`), `iat`, `exp`, and `jti`. |
| Token storage | Android stores only the bearer token in encrypted local storage. |
| Logout | Server revokes or denylists the token; Android clears local state regardless of the HTTP result. |
| Registration / login | Return `token`, not `accessToken`. |
| Session validation | `GET /auth/me` validates the token and returns the current user. |

The Android client expects a `token` property in authentication responses, uses lowercase `candidate` and `recruiter` role values in registration input, and treats a failed `/auth/me` call as an expired or invalid session. [file:2]

### 1.5 Internal service authentication

The gateway-to-matching-service interface is internal only. It must not be exposed through the public gateway or called directly by Android.

```http
POST /internal/matching/rank
X-API-Key: <MATCHING_SERVICE_API_KEY>
X-Request-Id: <request-id>
Content-Type: application/json
```

| Property | Contract |
|---|---|
| Caller | Fastify gateway only. |
| Authentication | `X-API-Key` shared secret or service token. |
| Correlation | `X-Request-Id` propagated from the public request. |
| Transport | HTTP on the internal Docker/service network; never public internet exposure. |
| Response | Ordered card IDs and scores; raw database rows must not be returned to Android. |
| Failure policy | Gateway returns a normalized public error; it may fall back to PostgreSQL-only recency ordering when the matching service is unavailable or exceeds its timeout. |

The SAD identifies the Express ranker’s current standalone `GET /feed/:candidateId` interface as an internal development interface, not an approved public API. The target internal contract is `POST /internal/matching/rank`, authenticated by a service key and correlated by `X-Request-Id`. [file:2]

## 2. Error Contract

Every non-2xx response from the public gateway uses this exact envelope:

```json
{
  "code": "string",
  "message": "string"
}
```

| HTTP status | `code` | When used |
|---|---|---|
| 400 | `BAD_REQUEST` | Malformed JSON, invalid UUID, or structurally invalid request. |
| 401 | `UNAUTHORIZED` | Missing, malformed, expired, or revoked bearer token. |
| 403 | `FORBIDDEN` | Authenticated user lacks the required role or resource ownership. |
| 404 | `NOT_FOUND` | Route, card, profile, swipe, or match does not exist or is not visible to caller. |
| 409 | `CONFLICT` | Duplicate email, duplicate idempotency key with a different request body, or conflicting state transition. |
| 422 | `VALIDATION_ERROR` | Semantically invalid field values, such as an unsupported role, action, decision, or consent failure. |
| 500 | `INTERNAL_SERVER_ERROR` | Unexpected gateway, database, or downstream-service failure. |
| 501 | `NOT_IMPLEMENTED` | Endpoint is intentionally not implemented in the current milestone. |
| 503 | `SERVICE_UNAVAILABLE` | Matching service unavailable and no safe fallback is available. |

Examples:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Please confirm the age requirement and accept the privacy notice."
}
```

```json
{
  "code": "UNAUTHORIZED",
  "message": "Authentication is required."
}
```

The gateway must normalize all errors to this shape, including Fastify validation failures and downstream matching-service failures. The current implementation returns Fastify’s default 404 body for unmatched URLs, which does not conform and must be corrected. [file:2]

## 3. Serialization Rules

| Rule | Contract |
|---|---|
| JSON property casing | Lower camelCase, for example `displayName`, `companyName`, `cardId`, `matchScore`. |
| Timestamps | ISO 8601 UTC, ending in `Z`, for example `2026-11-22T08:00:00.000Z`. |
| Identifiers | UUID v4 strings. |
| Nullable fields | Explicitly identified below; otherwise required and non-null. |
| Enums | Uppercase string values in API payloads: `CANDIDATE`, `RECRUITER`, `LIKE`, `PASS`, `GREEN_FLAG`, `RED_FLAG`, `ACCEPT`, `DECLINE`, `JOB`, `COMPANY`, `ACTIVE`, `MATCHED`, `DECLINED`. |
| Role input | Android sends lowercase `candidate` or `recruiter`; gateway accepts both cases and normalizes to uppercase internally. |
| Empty collections | Serialized as `[]`, never `null`. |
| Pagination | Cursor-based; absent `nextCursor` means no additional page. |

The Android DTOs use camelCase JSON names, lowercase role input during registration, and `token` as the authentication-response field. The gateway must serialize responses to match these client expectations. [file:2]

## 5. Authentication and GDPR Consent

### 5.1 `POST /auth/register`

Creates a candidate or recruiter account, records consent, creates a recruiter company membership when applicable, and returns a session token.

**Auth / role:** Public.  
**Headers:** `Content-Type: application/json`, `X-Request-Id` optional.  
**Idempotency:** Not required.

**Request schema**

| Field | Type | Required | Rules |
|---|---|---:|---|
| `email` | string | Yes | Valid email address; unique across accounts. |
| `password` | string | Yes | Minimum 8 characters. |
| `role` | string | Yes | `candidate` or `recruiter`; case-insensitive input, normalized to `CANDIDATE` or `RECRUITER`. |
| `displayName` | string | Yes | Non-empty after trimming. |
| `ageConfirmed` | boolean | Yes | Must be `true`. |
| `privacyAccepted` | boolean | Yes | Must be `true`. |
| `companyName` | string \| null | Conditional | Required when `role` is `recruiter`; otherwise `null` or omitted. |
| `companySector` | string \| null | Conditional | Required when `role` is `recruiter`; otherwise `null` or omitted. |

**Request example — candidate**

```json
{
  "email": "maya.candidate@example.com",
  "password": "Str0ngPassw0rd",
  "role": "candidate",
  "displayName": "Maya Chen",
  "ageConfirmed": true,
  "privacyAccepted": true,
  "companyName": null,
  "companySector": null
}
```

**Request example — recruiter**

```json
{
  "email": "liam.recruiter@example.com",
  "password": "Str0ngPassw0rd",
  "role": "recruiter",
  "displayName": "Liam Patel",
  "ageConfirmed": true,
  "privacyAccepted": true,
  "companyName": "Northwind Robotics",
  "companySector": "Manufacturing"
}
```

**Response — 201**

```json
{
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.example-signature",
  "user": {
    "id": "3f8c9a20-7d64-4d2e-9a1f-8b0f9d7f2a11",
    "email": "maya.candidate@example.com",
    "role": "CANDIDATE",
    "displayName": "Maya Chen"
  }
}
```

**Backend obligations**

- Hash passwords using a modern password-hashing algorithm.
- Persist consent version, consent timestamp, `ageConfirmed`, and `privacyAccepted`.
- Create the recruiter’s company on first recruiter sign-in when no membership exists.
- Return `409 CONFLICT` for an already-registered email.
- Return `422 VALIDATION_ERROR` when required consent fields are false or recruiter company data is missing.

The Android client sends lowercase role values and expects `token` plus a `user` wrapper. The SAD identifies consent persistence, duplicate-email handling, and company-membership timing as required backend behavior. [file:2]

## 7. Candidate Feed

### 7.1 `GET /candidate/feed`

Returns a ranked, role-scoped feed of unswiped cards for the authenticated candidate.

**Auth / role:** `CANDIDATE`.  
**Headers:** `Authorization: Bearer <jwt_token>`.  
**Query parameters**

| Parameter | Type | Required | Default | Rules |
|---|---|---:|---:|---|
| `limit` | integer | No | `20` | Minimum 1, maximum 50. |
| `cursor` | string | No | — | Opaque pagination cursor from `nextCursor`. |

**Response — 200**

```json
{
  "cards": [
    {
      "id": "9d2a7f30-5f2c-4a2e-8a7b-6c8d9e0f1a22",
      "kind": "JOB",
      "title": "Junior Backend Engineer",
      "companyName": "Northwind Robotics",
      "sector": "Manufacturing",
      "description": "Build and improve REST APIs for internal operations.",
      "location": "Santa Clara, CA",
      "contractType": "Full-time",
      "tags": ["Node.js", "TypeScript", "SQL"],
      "salaryRange": "$70,000 - $90,000",
      "matchScore": 8
    }
  ],
  "nextCursor": "eyJvZmZzZXQiOjIwfQ",
  "source": "MATCHING_SERVICE"
}
```

**Empty feed — 200**

```json
{
  "cards": [],
  "nextCursor": null,
  "source": "MATCHING_SERVICE"
}
```

**Contract rules**

- Only `PUBLISHED` cards with a publication date are eligible.
- Cards previously swiped by the candidate are excluded.
- `matchScore` is an integer score supplied by the matching service.
- `source` is `MATCHING_SERVICE` for ranked results or `POSTGRESQL_FALLBACK` for recency-only fallback.
- A `Company Card` may appear for discovery and ranking feedback but does not create a match.
- The gateway must not expose raw ranker rows, internal SQL fields, or graph internals to Android.

The Android client expects `cards` and currently sends no pagination arguments. The gateway must therefore support the Android default request while also providing optional `limit` and `cursor` for future client releases. [file:2]

## 8. Candidate Swipes and Flags

### 8.1 `POST /candidate/swipes`

Records a candidate decision on one card. Only candidates may call this endpoint.

**Auth / role:** `CANDIDATE`.  
**Headers:** `Authorization: Bearer <jwt_token>`, `Content-Type: application/json`, `Idempotency-Key: <uuid-v4>`.

**Request schema**

| Field | Type | Required | Rules |
|---|---|---:|---|
| `cardId` | string | Yes | UUID of an existing, visible card. |
| `action` | string | Yes | `LIKE`, `PASS`, `GREEN_FLAG`, or `RED_FLAG`. |

**Request example**

```json
{
  "cardId": "9d2a7f30-5f2c-4a2e-8a7b-6c8d9e0f1a22",
  "action": "LIKE"
}
```

**Response — 201**

```json
{
  "cardId": "9d2a7f30-5f2c-4a2e-8a7b-6c8d9e0f1a22",
  "action": "LIKE",
  "recorded": true
}
```

**Idempotency rules**

- A repeated request with the same `Idempotency-Key` and identical body returns the original `201` response and must not create another swipe.
- A repeated key with a different body returns `409 CONFLICT`.
- A missing, malformed, or duplicate-conflicting key returns the appropriate `400`, `422`, or `409` response.
- The key is scoped to the authenticated candidate.

**Behavior**

- `LIKE` on a `JOB` card makes the candidate eligible for recruiter review.
- `PASS` never creates a match.
- `GREEN_FLAG` and `RED_FLAG` record progressive feedback and may influence future ranking; they do not create a match.
- A `Company Card` like is ranking feedback only and never creates a match.
- The gateway validates candidate identity, card existence, card visibility, card kind, and company membership before persisting a swipe.

The Android app sends uppercase `LIKE` or `PASS`, a new UUID idempotency key per UI action, and removes the card locally only after a successful response. [file:2]

```json
    "recruiterId": "6a1d2b3c-4e5f-4a7b-8c9d-0e1f2a3b4c5d",
    "status": "MATCHED",
    "createdAt": "2026-11-22T08:20:00.000Z"
  }
}
```

**Response — `DECLINE`**

```json
{
  "swipeId": "b7e4b8d2-2a91-4c8e-9f61-0d3f7e8a9b33",
  "decision": "DECLINE",
  "match": null
}
```

**Match rules**

- Only candidates swipe.
- Only a recruiter authorized for the card’s company may decide.
- `ACCEPT` persists the decision and creates one match scoped to that recruiter and candidate.
- `DECLINE` removes the swipe from the interested list and creates no match.
- A candidate may receive separate matches from distinct authorized recruiters for the same card.
- The swipe decision and match creation must be atomic in PostgreSQL.

The SAD identifies the current one-decision / one-match-per-candidate-card schema as insufficient for distinct accepting recruiters; the backend must implement the required per-recruiter match cardinality before this endpoint is enabled. [file:2]

**Privacy rules**

- A candidate sees only matches in which they are the candidate.
- A recruiter sees only matches in which they are the accepting recruiter.

- Match status is participant-scoped and must not reveal another participant’s decision history.

|---|---|---|---|---|
| `GET /health` | Process liveness | None | None | None |

| `POST /auth/register` | Validation, password hashing, JWT issue, consent persistence | Create account, profile/company where applicable, consent record | None | Asynchronous profile/company projection |
| `POST /auth/login` | Credential verification, JWT issue | Read account and membership | None | None |
| `GET /auth/me` | Token validation and user serialization | Read account | None | None |

| `GET` / `PUT /candidate/profile` | Authorization and DTO mapping | Read/write candidate profile | Profile update projection | Graph profile synchronization |
| `GET /candidate/feed` | Authorization, matching call, card hydration, pagination | Read visible unswiped cards | Rank candidate/card candidates | Read graph-derived relationship signals |
| `POST /candidate/swipes` | Authorization, validation, idempotency, transaction | Create/replay swipe; update feed exclusion | Async interaction projection | Graph swipe/flag synchronization |

## 15. Implementation Acceptance Gates

The contract is complete only when the following tests pass:

- All public routes return the exact `{ "code": "string", "message": "string" }` error envelope.
- `POST /auth/register` persists consent version and timestamp.
- JWT expiry is at most 24 hours and logout revokes server-side access.
- Candidate profile reads and writes preserve the Android `profile` wrapper and camelCase fields.
- Feed results exclude previously swiped cards and return ranked card IDs and scores from the matching service.
- Matching-service failure produces a safe PostgreSQL recency fallback or a normalized `503` response.
- Swipe replay with the same `Idempotency-Key` produces no duplicate row.
- `PASS`, `GREEN_FLAG`, and `RED_FLAG` never create matches.
- Recruiter decisions enforce company membership and reject cross-company access.
- `ACCEPT` creates a participant-scoped match; `DECLINE` creates none.
- Two authorized recruiters can create distinct matches for the same candidate/card pair.
- `GET /matches` returns only participant-visible matches.
- Neo4j deletion or rebuild failure cannot prevent PostgreSQL privacy erasure.

These gates reflect the SAD’s identified contract, transaction, graph-projection, and operational gaps. [file:2]
